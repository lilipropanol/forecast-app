 How did we get here?
 ❖ Started with the WWW – aimed at browsing Hypertext Documents across the Internet
 ❖ TCP/IP around since 1974
           ◼      First link to Ireland - TCD (June, 1991)
 ❖ Internet penetration was primarily to Universities
           ◼      Main application was Email, telnet, (anonymous) ftp, etc.
 ❖ Could find useful data on other Internet sites (software, papers, etc.) and retrieve it using FTP
 ❖ Hardest part was to discover what is out there – and where?
           ◼      Resource Discovery (e.g., Cloud Service discovery, Google Search, etc.)
 ❖ Users at the time (early 1990s) were using a mix of Terminals, PCs (with and without Windows
 (1985), Mac (1984), X-windows (early 1980s)

 HTTP (HyperText Transfer Protocol) Overview
   ❖ Client Server model
             ▪ A request–response protocol
             ▪ Client requests, server responds
   ❖ Application layer protocol
             ▪ Assumes a reliable transport layer protocol
             ▪ Usually, Transmission Control Protocol (TCP)
                ▪ QUIC, new transmission layer protocol used by HTTP/3
   ❖ HTTP is:
             ▪ Connectionless
             ▪ Media Independent
             ▪ Stateless
   ❖ HTTP resources identified using Uniform Resource Locators (URLs)
             ▪ URLs are encoded as hyperlinks in HTML document

----- PAGE 4 -----

         HTTP Request Messages ‘Verbs’
   ❖ HTTP Verbs
      ▪ Define a set of request methods to indicate the purpose of the request and what is
        expected if the request is successful
      ▪ Although they can also be nouns, these request methods are sometimes referred to as
        HTTP verbs

   ❖ GET
      ▪ Requests resource
      ▪ Client wants to retrieve data only

   ❖ POST
      ▪ Client send data to the resource

   ❖ PUT, DELETE, CONNECT, OPTIONS, TRACE, PATCH
      ▪ Perform other useful actions
      ▪ Most important 2 are GET and POST
                                                   https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods
Trinity College Dublin, The University of Dublin                                                                  5

----- PAGE 5 -----

         HTTP Request Messages ‘Verbs’
   ❖ The less useful HTTP Verbs:
             ▪ PUT: replaces all current representations of the
               target resource with the request payload
             ▪ DELETE: deletes the specified resource
             ▪ CONNECT: establishes a tunnel to the server
               identified by the target resource
             ▪ OPTIONS: describes the communication options
               for the target resource
             ▪ TRACE: performs a message loop-back test along
               the path to the target resource
             ▪ PATCH: applies partial modifications to a resource



                                                   https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods

 Javascript Basics
   ❖ Syntax of language:
      ▪ Blocks of code, variables: Similar to Java
      ▪ Dynamically typed: No explicit type declarations
      ▪ No type checking
      ▪ Strict mode: Can use ‘Strict’ mode to force all variables to be declared
      ▪ No input-output as part of the language
      ▪ Can use the console, but the output doesn’t appear on the page

   ❖ JavaScript runs in a ‘Host Environment’ with Objects (host specific) available to:
      ▪ Get and Put output text, results, colours, sounds etc
             ▪ Events and Actions (e.g., clicks, F5) that JavaScript can ‘Hook on to’

               eventually
             ▪ A promise is either: pending, fulfilled, or rejected
   ❖ Executor Function
             ▪ Take two arguments: both functions (resolve, reject)

             ▪ Then call either resolve() or reject() to reflect the result in the promise

   ❖ When you call “new Promise”

             ◼ When it blocks (or completes) control returns to “p = new Promise”

 RESTful APIs: the most common APIs used across the web today
   ❖ Representational State Transfer (REST) is a style of API
             ▪ defined by Roy Fielding (developer of HTTP/1.1)
             ▪ A style of API that is ‘compatible with the HTTP object model’
             ▪ Proposed in his 2000 PhD thesis
                 ▪ An architectural style
                 ▪ That constrains the interface
             ▪ Client-Server Architecture
                 ▪ separate client and server concerns (e.g., UI/interaction for clients and storage/security for server)
             ▪ Statelessness
                 ▪ The server shouldn’t maintain state information for each client
                     ▪ Each request must contain all the information needed
                 ▪ The same request should get the same response
             ▪ Cachability: responses (from server) should indicate whether they can be cachable
             ▪ Layered System: client cannot distinguish between the real server and a proxy
             ▪ Code on demand (optional): Servers can extend client functionality (download executable code)
                                                         https://aws.amazon.com/what-is/restful-api, https://www.redhat.com/en/topics/api/what-is-a-rest-api

 RESTful APIs: Uniform Interface
   ❖ Core principles:
             ▪ Identification of Resources
                 ▪ Typically a one to one mapping of URI (Uniform Resource Identifier) to resource
                      ▪ i.e., clients interact with resources using their URIs
             ▪ Resource Manipulation by client via representations received
                 ▪ CRUD (create, read, update, and delete), i.e., POST, GET, PUT, DELETE in HTTP Verb
                 ▪ If the client has an object, it can delete or modify that object
                 ▪ Received representations contain enough information for manipulation of resource
             ▪ Self-Descriptive Messages
                 ▪ Each message (either request or response) contains all info to process the message
                      ▪ not dependent on context
             ▪ Hypermedia as the engine of application state
                 ▪ Client can use server-provided links for directions (i.e., possible actions next)

      ▪ has been available since IBM’s System 360 in
         the mid-1960s

 Grid Computing
   ❖ Popular term in the 1990s
   ❖ An analogy to the power grid
   ❖ Scientific community’s attempt to unify compute clusters
     into a single compute engine that could be temporarily
     assigned to one user.

   ❖ Federated Architecture
   ❖ reflecting University control over individual facilities
   ❖ Popularised by Ian Foster and Carl Kesselman book in 1998
   ❖ Grid computing concept largely replaced
   ❖ By cloud computing

   Datacenter Network Architectures
   ❖ Servers are combined into Racks
   ❖ Often each Rack will have a Top-of-Rack Switch
      ▪ e.g., 40 x 1 Gbps + 2 x 10Gbps uplinks
      ▪ Three-Tier DCN Architecture (less popular today) Access, aggregate and core
        layers

   ❖ Top-of-Rack Switches connect to
     Aggregation switches
   ❖ These Aggregation switches connect
     to Core switches
      ▪ which in turn connect to
        Carrier Ethernet Links
      ▪ Current max 400Gbps

 AWS Database Services - DynamoDB
   ❖ Serverless, NoSQL Database service
   ❖ At highest level, DynamoDB is a Key-Value Store
   ❖ It stores items in tables with one or a combination of attributes stored as a primary
     key
   ❖ Tables are partitioned and replicated for high availability, reliability and performance
   ❖ Architecture described in 2007 SOSP paper: Dynamo: Amazon’s Highly Available Key-
     value Store
     https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf
   ❖ Uses Leslie Lamport’s Paxos algorithm to achieve consensus among partitions
     https://lamport.azurewebsites.net/pubs/paxos-simple.pdf

 DynamoDB Points to Note
   ❖ It’s a NoSQL database with very high performance
      ▪ DynamoDB can handle 10 trillion requests per day and support peaks of more

   ❖ Read Performance is very high (and cheap)
   ❖ Write Performance lower (and more expensive)
   ❖ Highly Replicated with “Eventual Consistency” by default
